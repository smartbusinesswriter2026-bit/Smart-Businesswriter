## 8. Automated testing, tile cases, and the self-healing loop (build 1.115+)

This section is the reference for anyone debugging or extending the admin
self-healing system.  The admin page is served at `http://127.0.0.1:8021/admin-sbw.html`
and defaults to the **Self-Healing** panel.

### 8.1 What is built

- **`src/bp/product/paper_batch.py`** Ã¢â‚¬â€ generates one real paper per subject tile from the
  tile's published preset objective and declared figures.  The conductor runs with no
  framework wrapper, so the paper shows the tile's computation, not a PESTEL essay.
  Format selector: Word / Excel / Both.  The Excel workbook is the product's own
  `spreadsheets.to_xlsx` (Cover, Summary, Inputs, Working, Results, Notes, Record).
- **`src/bp/product/case_store.py`** Ã¢â‚¬â€ seeds and stores cases under
  `qa/cases/<subject>/<tile-slug>/case_NNN.json`.  246 cases seeded from published presets.
  `upload()` accepts JSON, CSV/TSV, XLSX (first worksheet), Word, PDF, TXT and images; table
  headers map automatically onto the method's input names, and the gate runs
  `validate_inputs` plus the method itself before writing.
- **`src/bp/product/case_runner.py`** Ã¢â‚¬â€ replays a case (status, computation with numeric
  tolerance, required paper phrases, workbook sheets).  A fail logs one `tile-case`
  error carrying the `case_id` and the instruction.  `run_cases` stores a run manifest
  under `state/case_runs/<run_id>/`.
- **`src/bp/product/auto_resolve.py`** Ã¢â‚¬â€ a `case_id` error is replayed by code (zero
  tokens); a legacy error with a stored problem uses deepseek-v4.1-flash then
  deepseek-v4-pro.  A fix is marked verified only when replay passes.
- **`src/bp/product/autoresearch.py`** Ã¢â‚¬â€ the Karpathy loop: picks the highest-impact open
  error, skips errors with neither a problem nor a case id (no model call), resolves a case
  by code and a problem by flash -> pro, and when no open errors remain it replays the
  whole 246-case suite and stops only when that passes.  Metric is errors-closed %.
- **`web/admin-sbw.html`** Ã¢â‚¬â€ Self-Healing panel with six tabs: Overview, Errors & fixes,
  Testing, Cases, Uploads, Tools.  Testing keeps subject sections (permanent), collapsible
  tile groups, tickable tiles (ticks survive a subsection switch and a reload), Format
  selector, Generate selected, progress, results table and download links.  Cases runs the
  stored tests and reports pass/fail.  Uploads is the single test-file store (picker or
  drag-and-drop) that both testers read.

### 8.2 Routes

- `GET /api/ops/papers/tiles`, `POST /api/ops/papers/batch`, `GET /api/ops/papers/batch/{id}`, `GET /api/ops/papers/batch/{id}/download?format=zip|docx|explainer`, `GET /api/ops/papers/runs`
- `GET /api/ops/cases`, `POST /api/ops/cases/seed`, `POST /api/ops/cases/upload`, `POST /api/ops/cases/run`, `GET /api/ops/cases/runs`, `GET /api/ops/cases/runs/{id}`, `GET /api/ops/cases/runs/{id}/file/{name}`
- `POST /api/ops/errors/resolve` Ã¢â‚¬â€ in-pipeline fix ladder.

### 8.3 How to debug a failing case

1. Run the case (Tile cases card -> Run, or `POST /api/ops/cases/run`).
2. Every case run saves its paper, workbook and explainers in `state/case_runs/<run_id>/`; the
   result carries `paper`, `workbook` and `explainer_file`, and the Quick-check result table
   shows pass/fail only while the paper-preview result table links each output to
   `/api/ops/cases/runs/{id}/file/{name}`.  A pass can be opened and read, not only a fail.
3. On fail, the error appears in the error log (`/api/ops/errors`) with `lane: tile-case`
   and the `case_id`.  The failing paper is in `state/case_runs/<run_id>/`.
4. Resolve: `POST /api/ops/errors/resolve` with the `error_id` Ã¢â‚¬â€ it replays the case by
   code and marks verified only on a pass.
5. If the case still fails, the message is the assertion that failed
   (status, computation value, or missing paper phrase).  Fix the pipeline, then re-resolve;
   the case re-runs in the loop's next cycle.
6. A verified fix is a stored regression: re-seed the case (`case_store.seed(overwrite=True)`)
   after a computation change so the expected result tracks the frozen core.

### 8.4 Non-negotiables that apply to this subsystem

- No invented evidence, sources, numbers or citations: a corpus page is cited only when a
  sentence in it matches the tile; a weak page is labelled background.
- A dimension with no citable evidence carries a labelled background paragraph from the
  weak sources the retriever saw; it is never filled with invented evidence.
- A case is accepted only when its inputs pass `validate_inputs` and the method runs.
- A fix is marked verified only when replay passes.
- Beam is not in the fix path; beam is prose/problem-generation, flash then pro fix.

### 8.5 What the case checker verifies

`case_runner._check` fails a case on any of: the wrong status; a missing expected
result key; a computed key the case does not expect; a numeric value outside a
relative `1e-9` tolerance; no expected result at all; a required paper phrase
missing; none of the first three computed values appearing in the paper; a missing
workbook sheet; or none of those values appearing in the workbook.  The paper and
workbook checks use any-of over the first three numeric results, so an intermediate
value the formatter does not print cannot cause a false failure.

### 8.6 Domain invariants

`case_invariants.py` checks that the numbers a case records also agree with each
other: the accounting equation, the ratio identities, the DuPont identity, the
break-even formulas, loan totals, NPV discounting, the IRR zero, WACC weights,
the DCF split, proforma totals, the sales projection, Gini/HDI bounds,
TAM >= SAM >= SOM, cap-table shares, the inventory reorder point and queue
utilisation.  A missing input or output key skips the invariant; a wrong
relationship fails the case.  This is the durable version of the checks the
statements tile used to need, applied to the other tiles.

### 8.7 The unified upload store

There is **one** upload facility, on the **Uploads** tab.  A file is dropped or picked once,
against a chosen subject and tile, and it is stored as a case under
`qa/cases/<subject>/<tile-slug>/case_NNN.json` with `origin: "uploaded"`.  The store is
shared: it is not duplicated per subject, and the Testing and Cases tabs carry no file
picker of their own.

The two testers differ only in what they hand back:

| Tester | Where | What it returns |
|---|---|---|
| Quick check | Cases tab | pass/fail, duration, error text.  No paper, workbook or explainer links. |
| Paper previews | Testing tab, source `uploaded` (or `both`) | the paper plus **Word**, **Excel** and **explainer** downloads. |

Upload path, always in this order: read the file -> parse it by extension -> map table
headers (or the JSON `inputs`) onto the tile's input names -> `validate_inputs` -> run the
method -> only then write the case.  A file that cannot be replayed is rejected with the
reason; it is never stored as a case that fails later.

Accepted formats: JSON, CSV/TSV, XLSX/XLSM (first worksheet), Word (`.docx`/`.docm`), PDF,
TXT/MD and images.  Limit 5 MB per file.  Several files can be picked or dropped at once,
and each is gated separately, so one bad file does not discard the good ones.

The dropzone (`#uploadDrop`) is a second way into the same handler
`uploadTestFiles(subject, tile, files)`; the picker and the drop run the same code.  A drop
outside the zone is cancelled so the browser does not navigate away from the console.

### 8.8 The explainer

Every paper-preview run writes `explainer.docx` into the run folder, into the ZIP, and behind
`?format=explainer` (served as Word).  It
carries, per tile: the objective, the prefilled instruction, the declared inputs, the
computed result, the evidence counts (cited sources, background pages, named gaps) and the
generation status Ã¢â‚¬â€ labelled **Generation**, never "test passed", because the pass/fail
authority is the case runner.

Every case run writes one `<case>_explainer.docx` per result plus a run-level `explainer.docx`.
The per-case file has a **Check** section: the status, the problems (or the sentence that
the computation, the invariants, the paper and the workbook all agree), and the evidence
counts.  The whole run saves its paper, workbook and explainers for a pass as well as a
fail, so a green result can be opened and read.

### 8.9 The tile paper is the computation record, and it is the same document as the download

The tile preview used to compose a framework-style paper Ã¢â‚¬â€ Introduction, Scope and Method,
a dimension block, Evidence Base, Discussion, What Would Change the Answer, Conclusion and
a References list that said "no sources were used".  That was the conductor's framework
outline, and it did not match what the student downloads.

It now does.  `paper_batch.generate_one` builds the same record the real download renders
and passes it through the **same renderer** (`session_paper.docx_bytes`), so the preview and
the download carry the same headings in the same order:

| Section | Content |
|---|---|
| Result | one sentence with the computed figures at the method's declared precision |
| Inputs and results | **What you declared**, then **What was computed** |
| Assumptions made | the frozen method's own assumptions |
| Limitations | the frozen method's own limitations |
| How the figures were checked | the frozen method's own test names |

There is no framework section, no "Scope and Method", no "Evidence Base", no "Discussion"
and no reference list.  A reference list appears only when a source was actually declared;
the tile paper never prints a bibliography over an empty corpus.

The combined `combined.docx` is built from the same sections, so it matches the individual
papers.  `case_runner._check` maps the two legacy phrases it may still meet in old case
files Ã¢â‚¬â€ `Declared inputs` becomes `What you declared`, and `References` / `Bibliography` /
`Works Cited` are not required, because the paper deliberately omits them.  Case files are
migrated to the new phrases as they are re-seeded.

### 8.10 Financial statements in the Testing tab, and the repair provider

The **Financial statements** tile is a service, not a frozen preset, so it is not in
`SUBJECT_DEFS["tools"]`.  `paper_batch.sections()` adds it to the Accounting / Bookkeeping
group explicitly, with `service: "statements"`, `supported: true` and `has_defaults: true`.
The Testing tab therefore lists it and runs it like any other tile.

`paper_batch.generate_one` special-cases a `service == "statements"` tile: it calls the
statements service the server injects through `configure(..., statements=...)`, using a

no API spend.  The paper carries the Income statement, Balance sheet, Statement of changes
in equity and Notes.  When the format asks for a workbook, the same record is written through
`spreadsheets.to_xlsx` from the statements appendix (the case sheet, statements, working

statements service requires the server's core attachment, so a direct call outside the
server returns `needs_input` with that reason.

Each tile result also carries its own `explainer.docx`, and the Testing tab's result table

## 10. Growth loop vs repair loop (design note, 2026-11-08)

This section records a decision, not a build.  It exists so a later enhancer does not
re-open the "let the system write its own agents" idea and land on the wrong side of it.

### 10.1 The distinction

The system has two loops that are easy to confuse:

- **Repair loop** (`autoresearch` + `auto_resolve`): picks an open error, replays it, fixes
  it, pins a regression case.  It creates nothing new; it only checks whether something that
  used to work still works.  It can be autonomous because a **reference implementation**
  exists for every one of its checks.
- **Growth loop** (proposed, human-gated): when a capability gap is logged Ã¢â‚¬â€ an instruction
  the system refuses as out of scope Ã¢â‚¬â€ the system scaffolds a new method, capability entry,
  preset and test sketch.  A human writes the logic, runs the suite, and only then is the
  capability committed and a case seeded.  The repair loop then protects it.

The growth loop is **not** the repair loop, and it is not autonomous.  It is a proposal
generator.  Its loop only starts *after* a human has supplied the reference implementation.

### 10.2 Why human approval is what makes it sound

The repair loop is sound because every step has a reference that exists independently of the
loop: the frozen method, the stored problem, the regression suite.  A capability gap has no
such reference Ã¢â‚¬â€ the code you write *is* the reference.  If a model wrote both the method
and the test, the test would pass by construction and prove nothing.

So the first gate is not a formality, it is the thing that makes verification possible:

**Human writes the method logic** (computation owner) is step one.  Everything the growth
loop does before that point is design lane.  Steps 1-2 are computation-owner work; steps
3-5 are automated.

### 10.3 How the two loops connect

```
Growth loop (human-gated)                Repair loop (autonomous)
------------------------------           ------------------------------
capability gap logged                    error logged (open)
   |                                        |
scaffold generated (design lane)         autoresearch picks it up
   |                                        |
human writes the method + tests          auto_resolve: replay the case
   |                                        |
human runs the suite                     if pass -> mark verified
   |                                        |
if green -> committed (computation       case pinned in qa/regression/
  owner change)                             |
   |                                        |
case_store seeds a case for the tile     regression suite replays it
   |                                        |
repair loop now has a reference          if a future change breaks it -> fail
```

The **connection point is the case store**.  The growth loop creates a new tile capability;
the case store seeds a case from its published preset; the repair loop now has a reference to
check against.  The two loops do not compete: the growth loop *creates* references, the
repair loop *protects* them.

### 10.4 Soundness gates (all must hold)

| Gate | Who enforces | What it prevents |
|---|---|---|
| Human writes the method logic | Computation owner | Invented formulas, silent substitutions |
| Human runs the suite | Computation owner | Green-by-construction tests |
| Frozen contract passes | `test_frozen_contract.py` | Unreviewed core changes |
| Case seeded from the preset | `case_store.seed` | A capability with no test |
| Repair loop replays the case | `auto_resolve` | A fix that does not actually work |
| Regression suite pins the fix | `regression_cases` | The same error reappearing |

Remove any gate and the growth loop stops being sound.

### 10.5 What to build when this is picked up (design lane, no core edits)

1. **Gap logging.**  `chat.start`'s `not_supported` path and the case runner's "no method"
   path call `ops_log.log_finding(rule="capability_gap", ...)` with the instruction, the
   subject and the refusal reason attached.  Today those refusals are shown to the user and
   then lost.
2. **Scaffold generator.**  Emits skeleton files into `qa/scaffolds/<subject>/<tile>/`: a
   method stub, a capability entry, a preset and a test sketch, all marked `PROVISIONAL` and
   none wired into the running system.  Before it writes anything it calls
   `error_db.growth_brief(subject, tile, instruction)` and puts that block at the top of the
   scaffold, so the new method is checked against the mistakes already paid for.
3. **A triage filter.**  The Validation panel gains `source=capability_gap`, so the backlog
   is "things users asked for that we cannot do yet" rather than a guess.
4. **A scaffold button.**  "Generate scaffold" on a gap finding writes the skeletons for a
   human to fill in.
5. **Read the error database.**  `qa/errors/error_registry.jsonl` is the memory; it holds a
   lesson for every fix (symptom, trigger, fix, artifact, files, tests, avoid).  The growth
   loop must read it before proposing a method, and add a lesson to it in the same change
   that adds a test.

The system captures the demand and scaffolds the shape; the human provides the substance.

### 10.6 What not to build

- **Autonomous code writing.**  The patch cannot be verified without a reference, and the
  reference is what the human writes.
- **Auto-wiring of scaffolds.**  A scaffold is a draft; wiring it in before review lets
  unverified computation into the frozen core.
- **Agent factory (agents creating agents).**  Recursive agent creation without a trust
  boundary is how runaway cost and unreviewed computation get into the product.

### 10.7 The honest boundary

What exists today is a **repair loop + a test harness + a case store**.  It is good at
detecting that something broke, verifying a fix by replay, keeping the fix durable, and
surfacing what it cannot fix.  It is not a software engineer, and it should not pretend to
be.  The step from "here is a gap" to "here is the code that closes it" needs judgment about
what the capability does, what it refuses, and how it fits the frozen contract Ã¢â‚¬â€ and that
judgment is the computation owner's.

### 11.5a The control set (R2) â€” the measurement checks itself

`qa/relevance/controls.json` holds the frameworks and capabilities the system
**already has**.  Every sweep runs them against what it read, and:

- a **framework** control holds only when the framework's name appears in an
  **evidence excerpt** â€” the catalogue already knows it exists, so checking
  the catalogue would pass whether or not the method could see it;
- a **capability** or **retrieval** control holds when the artefact is in the
  catalogue; these are not evidenced from the outside.

If the share of controls held falls below `min_controls_held` (0.75), **the
measurement failed and no gap is promoted from it** â€” the candidates are
withheld and the run says why.  A control that scores zero is evidence about
the *method*, not about the catalogue.

This rule exists because the Phase 1 research measured the same thing: reading
the sampling frame's core-course lists produced **zero** hits for every
framework, including the seven the system already has.  Two of the three
methods tried failed exactly this way, and nothing reported it until a control
was carried alongside the measurement.

## 12. The owner's switches and the growth loop

Read this section before changing the loops, the search chain or the admin
console's **Loops** tab.

### 12.1 The capability registry

`src/bp/product/ops_switches.py` holds every capability the owner may
switch.  A switch decides whether something **runs**; it never changes a
rule, a gate or a computation.

| Key | Kind | Default | What it does |
|---|---|---|---|
| `loop.repair` | loop | **off** | `autoresearch` — replays open errors, fixes what it can by replay, pins the fix as a regression case.  Creates nothing, applies no code. |
| `loop.growth` | loop | **off** | `growth_loop` — turns an approved capability gap into a PROVISIONAL scaffold for a human to finish. |
| `loop.relevance` | loop | **off** | `relevance.job` — sweeps the sampling frame for what schools teach and what the standards now require. |
| `search.brave` | search | on | The cheap, fast web search the RRA tries first. |
| `search.firecrawl` | search | on | The second provider: answers when Brave rate-limits. |
| `search.opengo` | search | on | The owner's backup: a headless OpenCode session running DeepSeek V4.1 Flash with its websearch tool. |

**Every loop is off by default.**  A switch turned on works immediately — the
loop starts on its next pass — and a switch turned off stops the thing.  The
state lives in `state/ops_switches.json`, so a switch survives a restart.
The env vars `BP_AUTORESEARCH_AUTOSTART`, `BP_GROWTH_AUTOSTART` and
`BP_RELEVANCE_AUTOSTART` **seed** a loop's switch the first time the system
looks; they are not the switch itself.

**The repair loop no longer starts by itself at boot.**  It used to, whenever
an error was waiting.  That behaviour is now `loop.repair`, and the default
is off.

### 12.2 The routes and the console

`GET /api/ops/loops` lists every capability with its state.
`POST /api/ops/loops/{key}/switch` with `{"enabled": true|false}` turns one
on or off, and the change takes effect immediately.

The console has a **Loops** tab under Self-Healing: a switch per capability,
the running state of each loop, and the reason each one is safe.

### 12.3 The growth loop

`src/bp/product/growth_loop.py` reads the open findings whose **rule** is
`capability_gap` — from the chat (`source="capability_gap"`) and from the
Relevance Research Agent (`source="relevance"`) alike — and writes a
PROVISIONAL scaffold under `qa/scaffolds/<subject>/<tile>/`:

| File | What it is |
|---|---|
| `method_stub.py` | the method's shape, with `impl` left to a human |
| `capability_entry.py` | the row the capability would add to `capabilities.ENTRIES` |
| `preset.json` | the tile preset, with the inputs left empty |
| `test_sketch.py` | the test's shape, so the suite cannot be green by construction |
| `README.md` | the gap, what the system already knows, the research order, and the checklist before it becomes a capability |

The loop **never** commits, **never** wires anything into the running
system, and **never** resolves the finding it worked on: the finding stays
open for the owner.  What it has scaffolded is recorded in
`state/growth_loop.jsonl`, and a gap is scaffolded once.

### 12.4 The search chain

The RRA searches `brave -> firecrawl -> opengo`.  When Brave and Firecrawl
rate-limit (HTTP 429), the OpenCode leg answers: a headless `opencode run`
session on the OpenCode Go gateway, running DeepSeek V4.1 Flash, using its
websearch tool with the site's domain in the prompt.

Four defects in that provider were found and fixed while wiring it:

1. the session was killed at the websearch **tool call**, before the tool
   returned its results, so the provider always returned nothing;
2. the parser read the older plain-text shape (`Title:` / `URL:`) while the
   tool now answers in **JSON** (`{"results": [{"url", "title", "excerpts"}]}`);
3. the **site filter never reached the prompt**, so every answer came from
   the open web and was then dropped by the curated filter;
4. a search that every provider **refused** was cached as "this source has
   nothing", so one rate-limited query poisoned the cache for its whole TTL.

Both shapes are read now, and a refused search is asked again rather than
served from the cache.
