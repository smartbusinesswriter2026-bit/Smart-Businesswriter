## 1. Why these tips matter

The tile could already prepare statements from a **trial balance**. What it could not do was read an
assignment — a transaction narrative, an adjustments problem, a cash-flow problem, an exam question —
and turn it into statements. The tips say where that capability actually lives: not in a bigger
prompt, and not in the page, but in a **split of responsibility**.

> The model reads language. Code does arithmetic. A check decides whether the answer is allowed out.

Everything below is that sentence, made concrete.

---

## 2. Tip 1 — the method

The owner's sequence for solving a statements problem, in their own order:

1. **Translate each transaction into debits and credits.** *"Paid $6,000 for a 12-month policy
   starting Feb. 1"* becomes Dr Prepaid Insurance, Cr Cash. **This is the only step that needs
   language understanding.**
2. **Identify what the text implies but does not state.** The 11/12 expired portion of insurance and
   rent, the accrued salaries, COGS under a periodic system, tax computed on pre-tax income. These
   are the **adjusting entries**.
3. **Post everything to accounts and compute balances.** In a workbook, this was the Computations
   sheet.
4. **Build the income statement** from the revenue and expense accounts. **Tax depends on pre-tax
   income, so it has to come after the other expenses are known.**
5. **Roll retained earnings forward**: opening balance plus net income minus dividends.
6. **Build the balance sheet** from the remaining accounts, each classified current/non-current and
   asset/liability/equity.
7. **Derive the indirect cash flow statement** from balance-sheet changes: each account's change goes
   to operating, investing or financing, with a sign convention per account type.
8. **Run the reconciliations.** Assets = liabilities + equity. Cash from the cash-flow statement =
   cash on the balance sheet. Ending cash = the simple sum of cash receipts minus cash payments.

> **The last check is the strongest.** Cash is computed two independent ways — from the cash
> transactions alone, and from the accrual-based statements. A mis-booked accrual or prepaid makes
> the two disagree.

### The design rules that follow from it

- **The model structures data; it does not do arithmetic.** An LLM can read *"paid $12,000 for 12
  months of rent starting Feb. 1"* and produce structured data. It must not add up numbers.
- **A strict journal entry schema**, carrying `source_text` and `assumptions` per entry so the
  output is auditable.
- **A chart-of-accounts table** with fixed properties (statement, section, normal balance,
  cash-flow treatment), so the engine looks an account up instead of deciding anything.
- **Adjusting entries are separate from transaction entries**, generated by explicit rules:
  `prepaid expired = amount × months elapsed ÷ total months`,
  `depreciation = (cost − residual) ÷ life` with a declared partial-year convention,
  `periodic COGS = beginning inventory + purchases − ending inventory`.
  The model extracts the parameters; the code does the maths.
- **Checks are non-negotiable**: trial balance debits = credits, the retained-earnings rollforward
  ties to the balance sheet, no account carries the wrong sign unless it is a contra. If a check
  fails the pipeline stops and reports which one.
- **Ambiguity is explicit.** A convention the text omits ("a full year of depreciation in the year of
  acquisition", the inventory system) is either asked for or written into a visible assumptions list.
- **Golden test cases**, run on every change.

## 3. Tip 2 — the implementation shape

Tip 2 supplied the concrete schemas and a working reference implementation. Its shape, retained here
because it is the contract the code follows:

| Piece | What it fixes |
|---|---|
| **Chart-of-accounts entry** (code, name, type, subtype, normal balance, statement, cash-flow bucket) | the engine never decides a classification; it looks one up |
| **Journal entry** (`original` / `adjustment` / `closing` / `plug`; balanced lines; source transaction id) | an unbalanced entry is unconstructible |
| **Extracted transaction** (id, date, raw text, kind, amounts, confidence) | the model's only output; no postings, no totals |
| **Adjustment spec** (references a registered function, never free text; carries the source problem text) | derived figures are code, and auditable |
| **Policy registry** (fiscal year end, rounding, depreciation convention, inventory system, tax rate, `explicitly_stated`) | every assumption is visible |
| **DAG node spec** (constant / function / tb_query / aggregate / projection, with dependencies) | tax cannot be computed before COGS; the order is proved, not hoped |
| **Minimal stdlib DAG evaluator** (deterministic topological sort, `Decimal`, one rounding point) | reproducible and replayable |
| **Articulation checks** (hard fail, never auto-correct) | a statement that does not tie is never emitted |

Two things Tip 2 flagged as needed before production, both honoured here:

- **an iterative pass** for adjustments that depend on adjusted results (tax depends on pre-tax
  income, which depends on the earlier adjustments). Implemented as two passes with the second one
  settling tax.
- **a per-engagement assumptions manifest.** Implemented as `statement_plan.manifest()`; the result
  travels with the build.

## 4. Tip 3 — compute scope is not output scope

The second pair of tips answers "what if a student only wants one statement?". The mistake to avoid
is two code paths — one that "just does the income statement" and one that "does everything". Two
paths drift: an IS net income that does not match the equity roll, a balance sheet that does not
balance. Tip 3's rule is the compiler rule:

> Always parse and type-check; emit only the requested target.

So the ledger is **always** built in full (it is aggregation, near-zero marginal cost, and it is what
makes every rendered statement articulate). What varies is which **projections** are rendered, and
which upstream projections are force-computed silently to keep them articulate.

### The dependency graph

```text
TB + DAG env ──► IS ──► RE ──► BS ──► CF
                  │      │      │
                  └──────┴──────┴──► (CF needs NI + ΔWC)
```

| Requested | Minimum work | Why |
|---|---|---|
| `IS` | the trial balance | an income statement stands alone |
| `RE` | IS + beginning RE + dividends | the roll-forward needs net income |
| `BS` | everything: all accounts, ending RE | RE closes through net income |
| `CF` (indirect) | IS + two balance sheets + non-cash detail | ΔWC and the cash endpoints |

The asymmetry is the product insight: **the income statement is the only statement that stands
alone.** A "balance sheet only" request is more expensive than an "income statement only" request.

### Two axes of "partial" — only one is safe

| Axis | Meaning | Safe? |
|---|---|---|
| partial **output** | full data extracted, user wants some statements | yes — gate rendering |
| partial **input**, IS only | user gave revenue/expense data and wants the IS | yes — the IS is self-contained |
| partial **input** + downstream | user gave partial data but wants a BS | only with plugs, and every plug must be named |

The code names the four shapes in `classify()`: `full_compute_partial_render`, `standalone_is`,
`requires_full_ledger`, `requires_plugs`. The tile only ever takes the first two; a plug is not
something it will do silently, because "no invented numbers" is the harder rule.

### The three properties the design buys

1. **Idempotency.** The same `(transactions, adjustments, policy)` yields the same trial balance
   whichever statements were requested. Partial output never changes the underlying numbers.
2. **No drift.** Asking for the IS and later for the BS re-renders the same ledger; it does not
   recompute a different one. `tests/test_product_statements.py` asserts the scalar records are
   equal across partial and full runs.
3. **Auditability.** The record says what was computed but hidden. When a client asks "where did the
   retained earnings figure come from?", the answer is in `computed`/`hidden`, not in a support
   email.

### What was adopted, and what is deliberately deferred

Adopted now (computation lane):

- the projection graph and `dependency_closure()` in `src/bp/statement_plan.py`;
- `classify()` for the four request shapes;
- request-scoped `present()`;
- `requested` / `computed` / `hidden` / `warnings` on the record;
- `verify_output()`, so a single-statement record is complete when that statement is present and an
  unrequested statement never leaks into the rendered set;
- instruction-text intent detection (`wants_statements()`), conservative: a mention is not a request;
- export of one statement.

Deferred on purpose:

- **plug mode** (`strict_articulation: false` with a `plugs` dict). The product never invents a
  figure, so there is nothing for the tile to plug; `classify()` names the shape for any future
  caller that is allowed to.
- **`comparative` and multi-period requests.** Out of scope until comparatives are modelled.
- **per-statement extraction prompts.** Tip 3 warns that "ignore balance-sheet items" is wrong (a
  loan brings interest, equipment brings depreciation). The tile therefore always extracts the whole
  journal and renders selectively, which is the tip's own "when in doubt" rule.

## 5. Tip 4 — the render layer (MiniMax's, specified here)

Tip 4 supplies the output design. Three ideas drive it:

1. **Every statement is a declarative line spec plus subtotal rules.** The model never composes a
   statement; it emits account metadata and line specs once per engagement. A renderer is a walk over
   the spec.
2. **`cf_bucket` on each account is the entire cash-flow reconciler.** Working-capital changes,
   non-cash addbacks and investing/financing splits are queries over metadata, not per-statement
   logic. One `_delta_wc()` walks the metadata and needs no account-specific branch.
3. **Signs are handled once, at the trial-balance boundary.** Past `tb.balance()` everything is
   presentation. No renderer flips a sign.

The metadata is the contract: `type`, `subtype`, `normal`, `statement`, `cf_bucket`, `bs_section`,
`bs_order`, `is_label`, `is_order`, `is_group`, `is_subtract`. The IS ordering, the BS sections, the
subtotal bases and the CF working-capital list are all filters/sorts over that dict — no hardcoded
per-statement account lists.

The cash flow is the interesting renderer because it produces three reconciliations as a side effect:

- CFO + CFI + CFF = the change in cash;
- that change equals the balance-sheet cash movement;
- ending cash in the statement equals the cash line on the balance sheet.

If any fires, the statement is not rendered. That is the same rule the computation lane already
enforces in `statement_plan.articulation()`, seen from the render side.

**Where this lives:** the render layer is MiniMax's to build — declarative line specs over the
frozen record, and the Excel/spreadsheet format the student downloads. The tips' renderer code is a
*specification of what the output must contain*, not a format decision. The handoff brief is
`docs/MINIMAX_STATEMENT_RENDER.md`: it states the record shape, the metadata it can rely on, the
three reconciliations it must preserve, and what it may not change.

## 6. What is now built (and where)

`src/bp/statement_plan.py`:

| Function | Tip it implements |
|---|---|
| `account()`, `validate_chart()` | the chart-of-accounts table; codes, roles and a retained-earnings account are required |
| `validate_entries()` | the strict journal schema, using the ledger's own balance rule |
| `money()`, `POLICY_DEFAULTS`, `manifest()`, `validate_policy()` | the policy registry and the visible assumptions list |
| `Node`, `toposort()`, `evaluate()` | the adjustment DAG: deterministic order, `$ref` dependencies, cycle refusal |
| `straight_line_depreciation`, `reducing_balance_depreciation`, `units_of_production_depreciation`, `prepaid_amortization`, `periodic_cogs`, `bad_debt_expense`, `tax_on_pretax`, `tax_benefit_on_loss` | the eight rule-based adjustments (plus `half_year` / `full_year` / `pro_rata` conventions); the registry also carries `none` |
| `resolve_adjustments()` | an adjustment becomes one balanced entry; a zero amount posts nothing and is reported |
| `build()` | compile → `accounts.build` → two-pass tax → articulation gate |
| `articulation()` | the three identities, including the two-way cash check |
| `PROJECTIONS`, `dependency_closure()`, `classify()` | Tip 3: what must be computed for a request, in topological order, and the four request shapes |

`src/bp/statement_extract.py`:

| Function | Tip it implements |
|---|---|
| `CONTRACT`, `system_prompt()`, `user_prompt()` | the model's brief: JSON only, chart codes only, no arithmetic |
| `parse()` | code fences stripped; anything but a JSON object refused |
| `validate()` | schema, account membership, the ledger's balance rule, **and grounding** |
| `extract()` | one `bp.llm` call, then the same validation; nothing partially accepted |

**The grounding rule is the load-bearing part.** Every amount the model proposes must appear in the
source text. An amount it derived — the 11/12 expired portion, the tax, the COGS — is refused, because
those belong to the adjustment stage. That is how "no invented numbers" stays true with a model in the
loop.

`src/bp/product/statements.py` (the request, not the computation):

| Function | Tip it implements |
|---|---|
| `wants_statements()` | Tip 3: the statements the instruction asks to see, or `None` for the full set; a mention is not a request |
| `_requested_statements()` | an explicit `statements` argument wins over the text; accepts `IS/RE/BS/CF` and the record keys |
| `PROJECTIONS`, `_scope()` | the rendered set, the computed closure and the hidden middle, without importing the core |
| `present(..., requested)` | Tip 3: the core's rendered text, scoped to the request |
| `_record(..., requested)` | `requested` / `computed` / `hidden` / `warnings` on the frozen record |
| `_reads_as_balances()` | a balances refusal stays a refusal; a transaction narrative is a job for the plan layer |
| `NoModel` | "nothing is configured" is retryable; a substantive refusal is final |

`src/bp/product/statements_verify.py`:

| Function | Tip it implements |
|---|---|
| `verify_reading()` | the seven reading checks (provenance, filing, chart, balance, articulation, completeness) |
| `verify_output()` | Tip 3: every requested statement is present, nothing unrequested leaked in, and a withheld cash flow carries its reason |

## 8. What is deliberately not built

- **Live extraction tuning.** `extract()` emits **adjustment specs** as well as journal entries: the
  model identifies the parameters (cost, life, convention, rate, prepaid payment and months, inventory
  counts, receivables balance and rate, tax rate) and names the function; the validator refuses any
  parameter that is not in the source text unless it is a declared default (residual 0, beginning
  inventory 0, total months 12). `to_policy` normalises the flat `depreciation_convention` a model may
  emit into the nested shape. The adjustment DAG then computes the amounts and posts them; a tax
  adjustment is settled in the second pass. This has been run on a synthetic 11-clause problem and on
  the smoke script; it is not tuned across many problems, and its accuracy on a real student's wording
  is unmeasured.
- **Multi-period comparatives, prior-period adjustment, consolidated statements, OCI depth.**
  Single entity, single period. `ledger` already carries OCI plumbing; the plan layer does not use it.
  Comparatives are refused with a named reason rather than merged.
- **Plug mode.** `classify()` names `requires_plugs` for a caller that is allowed to invent a balancing
  figure. The tile never plugs, because "no invented numbers" is the harder rule.
- **The render layer (declarative line specs, the `cf_bucket` reconciler, the Excel file).** This is
  MiniMax's lane; the brief is `docs/MINIMAX_STATEMENT_RENDER.md`. The record already carries the
  metadata it needs, and the three cash-flow reconciliations are already enforced by
  `articulation()`, so the renderer presents what is proved rather than proving it again.
- **The tile's reading path is only as good as its reader.** A trial balance is exact and
  deterministic. A transaction narrative depends on the model's extraction; when no model is
  configured, the tile says so and refuses instead of guessing.

## Tip 5 â€” How to solve problems involving financial statements (owner tip, 2026-11-04)

(Solving financial-statement problems is a process, not a single skill. Different problem types
require different entry points, but they share a common logic. Below is the complete framework.)

### The universal problem-solving framework (five steps)

1. **Identify the goal** â€” what exactly is being asked (prepare a statement, find a missing figure,
   analyze performance, correct an error). Prevents wasted computation.
2. **Map the given data** â€” list every figure and classify it (transaction, adjustment, beginning
   balance, ratio, â€¦). Reveals what you have and what you must derive.
3. **Choose the tool** â€” the right statement, formula or framework (accounting equation, cost-flow
   formula, ratio, cash-flow logic). Ensures method matches problem type.
4. **Work systematically** â€” follow the statement's structural order (revenues â†’ expenses â†’ net
   income; or operating â†’ investing â†’ financing). Prevents omissions and double-counting.
5. **Verify with a check** â€” balance check (A = L + E), cash reconciliation, or reasonableness test.
   Catches arithmetic and logic errors before submission.

### Problem types

**Type 1 â€” Preparing statements from transactions.** Set up a worksheet, journalize, post, adjust,
compute adjusted balances, then IS â†’ RE â†’ BS â†’ CF. Key links: net income â†’ RE; ending RE â†’ BS;
ending cash on CF = BS cash.

**Type 2 â€” Reconstructing missing figures.** Write the formula, substitute knowns, solve, cross-check
with a second relation. Core formulas: COGS = BI + purchases âˆ’ EI; gross profit = revenue âˆ’ COGS;
net income = revenue âˆ’ expenses; A = L + E; ending RE = beginning RE + NI âˆ’ dividends; current ratio,
D/E, ROA, inventory turnover, CFO = NI + non-cash âˆ’ increase in NWC.

**Type 3 â€” Ratio analysis.** Classify into liquidity / solvency / profitability / efficiency; compute
with correct year's figures (averages for balance-sheet items when instructed); compare across years,
against competitors, against industry; interpret what the number means and connect the ratios.

**Type 4 â€” Correcting errors.** Identify the erroneous entry and the correct one; compute the
correcting entry; trace through statements (NI, assets, liabilities/equity, cash); adjust each.
Common patterns: equipment expensed, revenue recorded but not delivered, depreciation omitted,
ending inventory overstated, accrued expense not recorded.

**Type 5 â€” Statement of cash flows (indirect).** NI + add-backs (depreciation, amortization, bad
debt) âˆ’ gains + losses; adjust working capital (CA increase subtract, CA decrease add, CL increase
add, CL decrease subtract); then investing (proceeds âˆ’ capex) and financing (borrowing/issuance âˆ’
repayments/dividends); reconcile beginning + change = ending cash = BS cash.

**Type 6 â€” From a trial balance.** Separate IS accounts (revenue/expense) from BS accounts (assets/
liabilities/equity); IS first, then RE, then BS; verify debits = credits and the sheet balances.

**Type 7 â€” Integrated case problems.** Read the whole case once without computing; build a numbered
transaction log; journalize; post; adjust; prepare IS â†’ RE â†’ BS â†’ CF; run the three checks; write
the analysis/memo last.

### Common pitfalls

- Forgetting to adjust prepaids for the correct number of months.
- Recording the full insurance/rent payment as an expense instead of splitting.
- Omitting accrued expenses.
- Computing tax on operating income instead of pre-tax income.
- Sign errors in the cash-flow statement.
- Double-counting a transaction.
- Not showing supporting computations.

### Compact checklist

â–¡ Goal identified and deliverable listed
â–¡ All given data classified (transaction / adjustment / beginning balance / ratio)
â–¡ Correct statement order followed (IS â†’ RE â†’ BS â†’ CF)
â–¡ Adjustments recorded separately from transactions
â–¡ Tax computed on pre-tax income
â–¡ Balance sheet balances (A = L + E)
â–¡ Ending cash on CF statement = cash on balance sheet
â–¡ Net income on IS = net income on RE statement
â–¡ All supporting computations shown
â–¡ Analysis/memo references specific figures or ratios
