## 1. Why these tips matter

The tile could already prepare statements from a **trial balance**. What it could not do was read an
assignment — a transaction narrative, an adjustments problem, a cash-flow problem, an exam question —
and turn it into statements. The tips say where that capability actually lives: not in a bigger
prompt, and not in the page, but in a **split of responsibility**.

> The model reads language. Code does arithmetic. A check decides whether the answer is allowed out.

Everything below is that sentence, made concrete.

---

## 2. Tip 1 — the method

The owner's sequence for solving a statements problem, in their own order:

1. **Translate each transaction into debits and credits.** *"Paid $6,000 for a 12-month policy
   starting Feb. 1"* becomes Dr Prepaid Insurance, Cr Cash. **This is the only step that needs
   language understanding.**
2. **Identify what the text implies but does not state.** The 11/12 expired portion of insurance and
   rent, the accrued salaries, COGS under a periodic system, tax computed on pre-tax income. These
   are the **adjusting entries**.
3. **Post everything to accounts and compute balances.** In a workbook, this was the Computations
   sheet.
4. **Build the income statement** from the revenue and expense accounts. **Tax depends on pre-tax
   income, so it has to come after the other expenses are known.**
5. **Roll retained earnings forward**: opening balance plus net income minus dividends.
6. **Build the balance sheet** from the remaining accounts, each classified current/non-current and
   asset/liability/equity.
7. **Derive the indirect cash flow statement** from balance-sheet changes: each account's change goes
   to operating, investing or financing, with a sign convention per account type.
8. **Run the reconciliations.** Assets = liabilities + equity. Cash from the cash-flow statement =
   cash on the balance sheet. Ending cash = the simple sum of cash receipts minus cash payments.

> **The last check is the strongest.** Cash is computed two independent ways — from the cash
> transactions alone, and from the accrual-based statements. A mis-booked accrual or prepaid makes
> the two disagree.

### The design rules that follow from it

- **The model structures data; it does not do arithmetic.** An LLM can read *"paid $12,000 for 12
  months of rent starting Feb. 1"* and produce structured data. It must not add up numbers.
- **A strict journal entry schema**, carrying `source_text` and `assumptions` per entry so the
  output is auditable.
- **A chart-of-accounts table** with fixed properties (statement, section, normal balance,
  cash-flow treatment), so the engine looks an account up instead of deciding anything.
- **Adjusting entries are separate from transaction entries**, generated by explicit rules:
  `prepaid expired = amount × months elapsed ÷ total months`,
  `depreciation = (cost − residual) ÷ life` with a declared partial-year convention,
  `periodic COGS = beginning inventory + purchases − ending inventory`.
  The model extracts the parameters; the code does the maths.
- **Checks are non-negotiable**: trial balance debits = credits, the retained-earnings rollforward
  ties to the balance sheet, no account carries the wrong sign unless it is a contra. If a check
  fails the pipeline stops and reports which one.
- **Ambiguity is explicit.** A convention the text omits ("a full year of depreciation in the year of
  acquisition", the inventory system) is either asked for or written into a visible assumptions list.
- **Golden test cases**, run on every change.

## 3. Tip 2 — the implementation shape

Tip 2 supplied the concrete schemas and a working reference implementation. Its shape, retained here
because it is the contract the code follows:

| Piece | What it fixes |
|---|---|
| **Chart-of-accounts entry** (code, name, type, subtype, normal balance, statement, cash-flow bucket) | the engine never decides a classification; it looks one up |
| **Journal entry** (`original` / `adjustment` / `closing` / `plug`; balanced lines; source transaction id) | an unbalanced entry is unconstructible |
| **Extracted transaction** (id, date, raw text, kind, amounts, confidence) | the model's only output; no postings, no totals |
| **Adjustment spec** (references a registered function, never free text; carries the source problem text) | derived figures are code, and auditable |
| **Policy registry** (fiscal year end, rounding, depreciation convention, inventory system, tax rate, `explicitly_stated`) | every assumption is visible |
| **DAG node spec** (constant / function / tb_query / aggregate / projection, with dependencies) | tax cannot be computed before COGS; the order is proved, not hoped |
| **Minimal stdlib DAG evaluator** (deterministic topological sort, `Decimal`, one rounding point) | reproducible and replayable |
| **Articulation checks** (hard fail, never auto-correct) | a statement that does not tie is never emitted |

Two things Tip 2 flagged as needed before production, both honoured here:

- **an iterative pass** for adjustments that depend on adjusted results (tax depends on pre-tax
  income, which depends on the earlier adjustments). Implemented as two passes with the second one
  settling tax.
- **a per-engagement assumptions manifest.** Implemented as `statement_plan.manifest()`; the result
  travels with the build.

## 4. What is now built (and where)

`src/bp/statement_plan.py`:

| Function | Tip it implements |
|---|---|
| `account()`, `validate_chart()` | the chart-of-accounts table; codes, roles and a retained-earnings account are required |
| `validate_entries()` | the strict journal schema, using the ledger's own balance rule |
| `money()`, `POLICY_DEFAULTS`, `manifest()`, `validate_policy()` | the policy registry and the visible assumptions list |
| `Node`, `toposort()`, `evaluate()` | the adjustment DAG: deterministic order, `$ref` dependencies, cycle refusal |
| `straight_line_depreciation`, `prepaid_amortization`, `periodic_cogs`, `tax_on_pretax` | the four rule-based adjustments (plus `half_year` / `full_year` / `pro_rata` conventions) |
| `resolve_adjustments()` | an adjustment becomes one balanced entry; a zero amount posts nothing and is reported |
| `build()` | compile → `accounts.build` → two-pass tax → articulation gate |
| `articulation()` | the three identities, including the two-way cash check |

`src/bp/statement_extract.py`:

| Function | Tip it implements |
|---|---|
| `CONTRACT`, `system_prompt()`, `user_prompt()` | the model's brief: JSON only, chart codes only, no arithmetic |
| `parse()` | code fences stripped; anything but a JSON object refused |
| `validate()` | schema, account membership, the ledger's balance rule, **and grounding** |
| `extract()` | one `bp.llm` call, then the same validation; nothing partially accepted |

**The grounding rule is the load-bearing part.** Every amount the model proposes must appear in the
source text. An amount it derived — the 11/12 expired portion, the tax, the COGS — is refused, because
those belong to the adjustment stage. That is how "no invented numbers" stays true with a model in the
loop.

## 5. Evidence that it works

The golden engagement in `tests/test_statement_plan.py` is **built from parameters**, not transcribed:
capital 50,000, loan 40,000, equipment 60,000, inventory 70,000 on credit, insurance 6,000 prepaid,
sales 120,000 cash + 80,000 credit, collections 65,000, payables 55,000, salaries 35,000 + 3,000
accrued, rent 12,000, interest 2,400, ending inventory 10,000, depreciation 60,000 over 5 years
full-year, insurance 11 of 12 months, tax 25%.

Hand-derived and asserted:

| Figure | Value |
|---|---|
| Revenue | 200,000 |
| Expenses | 129,900 |
| Pre-tax income | 70,100.00 |
| Tax (25%) | 17,525.00 |
| Net income | 52,575.00 |
| Total assets | 178,100.00 |
| Total liabilities | 75,525.00 |
| Total equity | 102,575.00 |
| Operating cash flow | 74,600 |
| Investing / financing | −60,000 / 90,000 |
| Net cash movement | 104,600 |

All three articulation identities pass, and the gate is proved **both ways**: a doctored record with
`total_assets` changed by 1.00 fails `assets_equal_liabilities_plus_equity`, and a doctored
`cash_flow.net_direct` fails the cash check.

The earlier probe (`qa/manual/tip-northstar-probe.py`) measured a different, fully worked engagement
through the same core: net income **42,075**, total assets **164,100**, operating cash flow **59,600**,
9 checks passed and 2 not applicable. It is kept as a measurement, not as product text.

## 6. What is deliberately not built

- **Live extraction tuning.** `extract()` now emits **adjustment specs** as well as journal
  entries: the model identifies the parameters (cost, life, convention, prepaid payment and months,
  inventory counts, tax rate) and names the function; the validator refuses any parameter that is not
  in the source text unless it is a declared default (residual 0, beginning inventory 0, total months
  12). `to_policy` normalises the flat `depreciation_convention` a model may emit into the nested
  shape. The adjustment DAG then computes the amounts and posts them; a tax adjustment is settled in
  the second pass. This has been run once on a synthetic 11-clause problem and produced depreciation
  12,000, prepaid 5,500, COGS 60,000 and tax on a pre-tax income of 69,600, with all eleven checks
  passing. It is not tuned across many problems and is not wired to the tile.
- **Reducing-balance / units-of-production depreciation.** Only straight-line is registered; the
  policy validator refuses any other method rather than pretending.
- **A tax benefit on a loss.** A loss computes no tax and says so; no deferred tax is modelled.
- **Multi-period comparatives, prior-period adjustment, consolidated statements, OCI depth.**
  Single entity, single period. `ledger` already carries OCI plumbing; the plan layer does not use it.
- **The tile's reading layer.** The tile now reads **transaction narratives** as well as trial
  balances, and **derives adjusting entries** from the text: prepaids, depreciation, COGS and tax are
  extracted as parameters, computed by the DAG, and posted, with the three articulation identities
  gating the output. It has been run once on a synthetic 11-clause problem (depreciation 12,000,
  prepaid 5,500, COGS 60,000, tax 17,400) and is not tuned across many problems. Multi-period and
  consolidated statements are out of scope.
- **Two display defects recorded in the Ashgrove case study**: ratios print at 28 decimals instead of
  the declared 3 dp, and brought-forward retained earnings is labelled "other" with truncated roll-
  forward labels. Both are in the record-packing code, not the browser.
